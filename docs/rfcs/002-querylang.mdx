# RFC 002: QueryLang — Data-Aware Filter DSL and Pipeline Body

**Status**: Draft  
**Depends on**: RFC 001 (Schema Registry)  
**Created**: 2026-05-09

## Summary

Two interlocking additions to the platform:

1. **FilterLang** — a standalone filter expression DSL (`KEY OP VALUE`) that compiles to
   ClickHouse WHERE clause SQL using schema registry type information. Users write
   `status = 200` and the system generates the correct SQL regardless of whether `status`
   is a static Int64 column, an attribute stored as String, or a field with conflicted
   type history.

2. **PQL (Pipeline Query Language)** — a PRQL-inspired pipeline syntax that replaces
   `NODE name\nSQL > ...` blocks as the body of a `.pipe` file. The existing PipeLang
   metadata directives — `DESCRIPTION`, `TAGS`, `TYPE`, `DATASOURCE`, `TARGET_DATASOURCE`,
   `COPY_SCHEDULE` — are **completely unchanged**. Only the query body changes.

### What stays the same in PipeLang

```
DESCRIPTION Daily revenue by country   ← unchanged
TAGS revenue, sales                    ← unchanged
TYPE ENDPOINT                          ← unchanged (ENDPOINT | MATERIALIZED | COPY)
DATASOURCE orders                      ← unchanged
TARGET_DATASOURCE summary              ← unchanged (COPY pipes)
COPY_SCHEDULE 0 * * * *               ← unchanged (COPY pipes)
```

### What changes: the query body

Old (NODE blocks with raw SQL):
```
NODE filter_orders
SQL >
  SELECT * FROM orders WHERE status = 200

NODE daily
SQL >
  SELECT toStartOfDay(ts) AS day, sum(amount) AS revenue
  FROM filter_orders GROUP BY day
```

New (PQL pipeline, PRQL-inspired):
```
from orders
filter status = 200
derive { day = toStartOfDay(ts) }
group { day } ( aggregate { revenue = sum(amount) } )
```

Legacy `NODE + SQL >` pipes continue to work unchanged — the parser detects which
syntax is present and dispatches accordingly.

## Motivation

### The Pain: Type Drift and JSON Extraction in SQL Nodes

Today a pipe author writes raw SQL inside `NODE` blocks. When the underlying DataSource
has dynamic attributes or type drift, the SQL quickly becomes defensive:

```sql
-- Inside a NODE SQL > block, filtering on a DataSource with dynamic attributes
SELECT
    toStartOfDay(observed_timestamp) AS day,
    country,
    sum(amount) AS revenue
FROM orders
WHERE
    -- status was ingested as String for a year, then switched to Int64
    (JSONExtractString(attributes, 'status') = '200'
     OR JSONExtractInt(attributes, 'status') = 200)
    -- env and environment are two names for the same concept in different sources
    AND (JSONExtractString(attributes, 'env') = 'prod'
         OR JSONExtractString(attributes, 'environment') = 'prod')
GROUP BY day, country
```

The author knows what they want. The JSON extraction and type hedging are noise
forced by lack of schema awareness in the query layer.

The same pipe in PQL, with FilterLang handling type resolution:

```
from orders
filter status = 200 AND env = prod
derive { day = toStartOfDay(observed_timestamp) }
group { day, country } ( aggregate { revenue = sum(amount) } )
```

FilterLang consults the schema registry, knows `status` is Int64 in attributes and
`env` aliases `environment`, and generates the correct ClickHouse SQL automatically.

### The Goal: Simplicity as a First Principle (Inspired by SigNoz)

SigNoz (observability platform on ClickHouse) lets users write `service.name = 'api'`
and handles type routing automatically because they know their schema. We extend that
principle to an arbitrary analytical platform with a dynamic schema: the schema registry
(RFC 001) gives us the same knowledge, applied generically.

The target: `status = 200 AND env = prod` compiles correctly whether `status` is a static
Int64, a String attribute, a Dynamic field with type history, or all of the above across
time.

### Prior Art

| System | Query abstraction | Schema-aware? | Compiles to |
|--------|------------------|---------------|-------------|
| PRQL | Pipelined transforms (from/filter/group/aggregate) | At compile time only | SQL |
| Malloy | Semantic model + views (measures/dimensions) | Yes, via source definitions | SQL |
| SigNoz | `KEY OP VALUE` filter DSL | Yes, fixed schema | ClickHouse SQL |
| dbt | Jinja-templated SQL | No — manual COALESCE/CAST | SQL |
| SQLMesh | SQL + Python models | No — explicit CAST encouraged | SQL |

Our design takes PRQL's pipelined structure, Malloy's schema propagation through transforms,
and SigNoz's type-transparent filter syntax — all on top of a dynamic schema (the registry).

## Layer 1: FilterLang Grammar

### Design Principles

- **Type-transparent**: `status = 200` works whether status is String, Int64, or Dynamic
- **Bare words**: `env = prod` is valid (system infers String from context)
- **Explicit cast**: `session_id::Int64 = 200` overrides registry resolution
- **Jinja-first**: Jinja templates render before FilterLang parsing; the grammar never sees `{{ }}`
- **SQL-embeddable**: output is a valid ClickHouse WHERE clause fragment

### ANTLR4 Grammar: `pkg/grammars/filtergrammar/FilterLang.g4`

```antlr4
// FilterLang.g4 — schema-aware filter expression DSL
// Operator precedence (lowest to highest): OR < AND < NOT < atom
grammar FilterLang;

filterExpr : filter EOF ;

filter
    : filter OR filter       # OrExpr
    | filter AND filter      # AndExpr
    | NOT filter             # NotExpr
    | '(' filter ')'         # GroupExpr
    | condition              # AtomExpr
    ;

condition
    : path CAST_OP typeName OP scalar     # CastCompare
    | path OP scalar                      # Compare
    | path IN '(' scalarList ')'          # InList
    | path NOT IN '(' scalarList ')'      # NotInList
    | path HAS scalar                    # HasElement
    | path HAS_ANY '(' scalarList ')'    # HasAny
    | path HAS_ALL '(' scalarList ')'    # HasAll
    | path CONTAINS scalar               # Contains
    | path NOT CONTAINS scalar           # NotContains
    | path LIKE scalar                   # Like
    | path ILIKE scalar                  # ILike
    | path NOT LIKE scalar               # NotLike
    | path MATCHES scalar                # Matches
    | path EXISTS                        # ExistsCheck
    | path NOT EXISTS                    # NotExistsCheck
    | path IS NULL                       # IsNull
    | path IS NOT NULL                   # IsNotNull
    ;

// a, a.b, a.b.c — dot-path for nested attribute access
path        : IDENT (DOT IDENT)* # FieldPath ;
typeName    : IDENT               # TypeName  ;   // e.g. Int64, String, Float64
scalarList  : scalar (COMMA scalar)* ;

scalar
    : STRING       # ScalarString
    | INTEGER      # ScalarInt
    | FLOAT        # ScalarFloat
    | BOOL         # ScalarBool
    | NULL         # ScalarNull
    | UNQUOTED_WORD # ScalarBareWord   // env = prod (no quotes)
    ;

OP       : '=' | '!=' | '<' | '>' | '<=' | '>=' ;
CAST_OP  : '::' ;
DOT      : '.' ;
COMMA    : ',' ;

AND      : A N D ; OR : O R ; NOT : N O T ;
IN       : I N ; HAS : H A S ;
HAS_ANY  : H A S '_' A N Y ;
HAS_ALL  : H A S '_' A L L ;
CONTAINS : C O N T A I N S ;
LIKE     : L I K E ; ILIKE : I L I K E ;
MATCHES  : M A T C H E S ;
EXISTS   : E X I S T S ;
IS       : I S ; NULL : N U L L ;
BOOL     : T R U E | F A L S E ;

INTEGER      : '-'? DIGIT+ ;
FLOAT        : '-'? DIGIT* '.' DIGIT+ ;
STRING       : '\'' (~['\\\r\n] | '\\' .)* '\''
             | '"' (~["\\\r\n] | '\\' .)* '"' ;
IDENT        : [a-zA-Z_][a-zA-Z0-9_]* ;
UNQUOTED_WORD: [a-zA-Z0-9_\-]+ ;   // lower priority than all keywords
WS           : [ \t\r\n]+ -> skip ;

fragment A:[Aa]; fragment N:[Nn]; fragment D:[Dd]; fragment O:[Oo];
fragment R:[Rr]; fragment I:[Ii]; fragment S:[Ss]; fragment H:[Hh];
fragment E:[Ee]; fragment X:[Xx]; fragment T:[Tt]; fragment L:[Ll];
fragment K:[Kk]; fragment C:[Cc]; fragment U:[Uu]; fragment M:[Mm];
fragment G:[Gg]; fragment F:[Ff]; fragment Y:[Yy]; fragment B:[Bb];
fragment W:[Ww]; fragment P:[Pp]; fragment DIGIT:[0-9];
```

### Path Resolution

The compiler consults the schema registry to resolve each `path` in a condition:

```
Resolve("status")
  1. Is "status" a static column?           → NO
  2. Is "status" in the attribute registry? → YES: {String:3000, Int64:5000}, DYNAMIC
  → Location: ATTRIBUTE, Type: DYNAMIC

Resolve("amount")
  1. Is "amount" a static column?           → YES: Float64
  → Location: STATIC, Type: FLOAT64

Resolve("env")
  1. Static column?                         → NO
  2. Attribute registry?                    → YES: {String:12000}, confidence 99%
  → Location: ATTRIBUTE, Type: STRING

Resolve("attributes.env")
  1. Multi-segment path, first = "attributes"
  2. Lookup "env" in attribute registry     → String, confidence 99%
  → Location: ATTRIBUTE, Type: STRING  (explicit path prefix, same result)

Resolve("unknown_field")
  1. Static?  NO
  2. Registry? NO
  → Location: UNKNOWN
  → Warning: "Field 'unknown_field' not in schema. Filter may return no results."
  → CompileAs: attributes.unknown_field::String (best-effort)
```

### Type Coercion Matrix

```
STATIC String,     user: status = 200        → status = '200'
STATIC String,     user: status = 'ok'       → status = 'ok'
STATIC Int64,      user: amount = '100'      → amount = 100
STATIC Int64,      user: amount = 100        → amount = 100
STATIC Float64,    user: score = 99          → score = toFloat64(99)
STATIC Bool,       user: active = 1          → active = true
STATIC Bool,       user: active = true       → active = true
STATIC DateTime64, user: ts = '2024-01-01'  → ts = parseDateTimeBestEffort('2024-01-01')
STATIC DateTime64, user: ts = 1704067200    → ts = fromUnixTimestamp64(1704067200)

ATTR String (99%), user: env = prod         → attributes.env::String = 'prod'
ATTR Int64 (95%),  user: status = 200       → attributes.status::Int64 = 200
ATTR Dynamic,      user: x = 200            → (attributes.x::String = '200'
                                                OR attributes.x::Int64 = 200)
ATTR Dynamic,      user: x::Int64 = 200     → attributes.x::Int64 = 200
UNKNOWN field,     user: foo = 'bar'        → attributes.foo::String = 'bar' + WARNING
```

### Operator → ClickHouse SQL

```
STATIC String "col":
  col = 'v'           → col = 'v'
  col != 'v'          → col != 'v'
  col LIKE 'v%'       → col LIKE 'v%'
  col ILIKE 'V'       → lower(col) = lower('V')
  col CONTAINS 'sub'  → position(col, 'sub') > 0
  col NOT CONTAINS    → position(col, 'sub') = 0
  col MATCHES 'p.*'   → match(col, 'p.*')
  col IN ('a','b')    → col IN ('a','b')
  col EXISTS          → isNotNull(col) AND col != ''
  col IS NULL         → isNull(col)

ATTRIBUTE String "env" (ClickHouse 25.x new JSON type):
  env = 'prod'        → attributes.env::String = 'prod'
  env CONTAINS 'pr'   → position(attributes.env::String, 'pr') > 0
  env EXISTS          → JSON_EXISTS(attributes, '$.env')
  env IS NULL         → attributes.env IS NULL

ATTRIBUTE DYNAMIC "status" (type conflict):
  status = 200        → (attributes.status::String = '200'
                         OR attributes.status::Int64 = 200)
  status::Int64 = 200 → attributes.status::Int64 = 200

ARRAY ATTRIBUTE "tags":
  tags HAS 'prod'           → has(attributes.tags::Array(String), 'prod')
  tags HAS_ANY ('a','b')    → hasAny(attributes.tags::Array(String), ['a','b'])
  tags HAS_ALL ('a','b')    → hasAll(attributes.tags::Array(String), ['a','b'])

STATIC Array "roles":
  roles HAS 'admin'         → has(roles, 'admin')

COLUMN ALIAS (if 'country' aliases ['geo_country_code']):
  country = 'US'     → (country = 'US'
                        OR attributes.geo_country_code::String = 'US')
```

| Where | How |
|-------|-----|
| `filter` transform in a PQL pipeline | schema from `DATASOURCE` declaration, propagated through prior transforms |

| `join` condition in PQL | FilterLang condition with access to both sides' schemas |
| CLI `lint` | validates filter against registry offline |

## Layer 2: PQL — PRQL-Inspired Pipeline Body

### Design Philosophy

PipeLang handles **metadata** (DESCRIPTION, TAGS, TYPE, DATASOURCE, etc.) and continues
to do so unchanged. The **body** of the pipe — what was `NODE name\nSQL > ...` — becomes
a linear PRQL-inspired pipeline.

PRQL's core insight: a query is a sequence of transforms where each step narrows, reshapes,
or aggregates the previous step's output. Reading top-to-bottom tells you exactly what the
data went through. SQL's problem is that the logical order of thought (filter early, then
group, then sort) doesn't match the written order (SELECT → FROM → WHERE → GROUP BY →
ORDER BY → LIMIT). PQL follows the logical order.

Key differences from PRQL:
- `filter` uses **FilterLang** syntax — schema-aware, type-transparent, no `==` confusion
- Expressions (in `derive`, `aggregate`) are **ClickHouse-native** — `toStartOfDay`, `quantile(0.95)`, `uniqExact`
- Jinja templates (`{{ param | default(x) }}`) render before PQL parsing — parameterization is first-class
- No separate `.prql` file — the PQL pipeline IS the `.pipe` body when there are no `NODE` keywords
- ClickHouse-specific extensions: `array_join`, `FINAL`, `SETTINGS`

### Backward Compatibility

Detection is automatic: if the pipe file body contains the `NODE` keyword → legacy parser.
No `NODE` keyword → PQL parser. Both parsers produce the same `Pipe` struct; the rest of
the system (executor, HTTP handler, scheduler, SQLMesh builder) is unchanged.

### PQL With Each Pipe Type

**TYPE ENDPOINT** — live parameterized query, exposed as REST API:
```
DESCRIPTION Top countries by revenue
TAGS revenue, api
TYPE ENDPOINT
DATASOURCE orders

from orders
filter env = prod
  AND observed_timestamp >= {{ start | default('2024-01-01') }}
group { country } (
  aggregate { revenue = sum(amount), orders = count() }
)
sort { -revenue }
take {{ limit | default(10) }}
```

**TYPE MATERIALIZED** — pre-computed ClickHouse materialized view, managed by SQLMesh:
```
DESCRIPTION Daily revenue summary (pre-aggregated)
TYPE MATERIALIZED
DATASOURCE orders

from orders
filter env = prod
derive { day = toStartOfDay(observed_timestamp) }
group { day, country } (
  aggregate { revenue = sum(amount), order_count = count() }
)
```

**TYPE COPY** — scheduled SQL-to-table write, runs on cron:
```
DESCRIPTION Copy last 24h of orders to cold storage
TYPE COPY
DATASOURCE orders
TARGET_DATASOURCE orders_archive
COPY_SCHEDULE 0 2 * * *

from orders
filter observed_timestamp >= now() - toIntervalDay(1)
  AND env = prod
select { user_id, amount, country, observed_timestamp }
```

### Full PQL Example — ENDPOINT with JOIN

```
DESCRIPTION Daily revenue by country with JOIN enrichment
TAGS revenue, sales
TYPE ENDPOINT
DATASOURCE orders

from orders
filter status = 200
  AND country IN ('US', 'UK', 'DE')
  AND observed_timestamp >= {{ start | default('2024-01-01') }}
  AND amount > {{ min_amount | default(0) | float }}
derive {
  day = toStartOfDay(observed_timestamp),
  tier = multiIf(amount > 1000, 'high', amount > 100, 'medium', 'low')
}
group { day, country, tier } (
  aggregate {
    revenue = sum(amount),
    order_count = count(),
    unique_users = uniqExact(user_id),
    p95_latency = quantile(0.95)(response_time_ms)
  }
)
join side:left dim_country (country = dim_country.code)
filter revenue > 1000
sort { -day, revenue }
take {{ limit | default(100) }}
skip {{ offset | default(0) }}
```

Compiled ClickHouse SQL:

```sql
WITH
  __derive AS (
    SELECT *,
      toStartOfDay(observed_timestamp) AS day,
      multiIf(amount > 1000, 'high', amount > 100, 'medium', 'low') AS tier
    FROM orders
    WHERE attributes.status::Int64 = 200
      AND country IN ('US', 'UK', 'DE')
      AND observed_timestamp >= parseDateTimeBestEffort('2024-01-01')
      AND amount > 0.0
  ),
  __agg AS (
    SELECT
      day, country, tier,
      sum(amount)                              AS revenue,
      count()                                  AS order_count,
      uniqExact(user_id)                       AS unique_users,
      quantile(0.95)(attributes.response_time_ms::Float64) AS p95_latency
    FROM __derive
    GROUP BY day, country, tier
  ),
  __join AS (
    SELECT __agg.*, dim_country.region
    FROM __agg
    LEFT JOIN dim_country ON __agg.country = dim_country.code
  )
SELECT *
FROM __join
WHERE revenue > 1000
ORDER BY day DESC, revenue ASC
LIMIT 100
OFFSET 0
```

### Grammar: `PQL.g4`

```antlr4
// PQL.g4 — PRQL-inspired pipeline query language
// Parses the body of a .pipe file when no NODE keyword is present.
// Jinja rendering happens BEFORE this parser runs.
grammar PQL;

pipeline : transform+ EOF ;

transform
    : fromTransform
    | filterTransform
    | deriveTransform
    | selectTransform
    | groupTransform
    | joinTransform
    | arrayJoinTransform
    | sortTransform
    | takeTransform
    | skipTransform
    | windowTransform
    ;

// ─── Transforms ────────────────────────────────────────────────────────────

// from table_name [final]
// 'final' maps to ClickHouse FINAL modifier for ReplacingMergeTree
fromTransform
    : KW_FROM IDENT KW_FINAL?
    ;

// filter condition [continuation lines]
// condition is parsed by the FilterLang parser (separate pass after Jinja render)
// multi-line: subsequent indented lines continue the same FilterLang expression
filterTransform
    : KW_FILTER filterLine (INDENT filterLine)*
    ;
filterLine : REST_OF_LINE ;

// derive { name = expr [, name = expr]* }
// One or more named computed columns added to each row (no grouping)
deriveTransform
    : KW_DERIVE '{' assignmentList '}'
    ;

// select { col [, col]* }  OR  select { name = expr [, name = expr]* }
// Projection — optional, default is SELECT *
selectTransform
    : KW_SELECT '{' selectionList '}'
    ;

// group { key [, key]* } ( aggregate { name = expr [, name = expr]* } )
// GROUP BY + aggregation combined — always appear together
groupTransform
    : KW_GROUP '{' keyList '}' '(' KW_AGGREGATE '{' assignmentList '}' ')'
    ;

// join [side:left|right|inner|full] table_name (filter_condition)
// join condition is a FilterLang expression referencing both sides
// shorthand: (==col_name) means this.col_name = that.col_name
joinTransform
    : KW_JOIN (KW_SIDE ':' joinSide)? IDENT '(' joinCond ')'
    ;
joinCond
    : '==' IDENT                    # SelfJoinCond   // (==user_id) shorthand
    | filterLine                    # ExplicitCond   // (user_id = sessions.uid)
    ;
joinSide : KW_INNER | KW_LEFT | KW_RIGHT | KW_FULL ;

// array_join column_name [as alias]
// ClickHouse-specific: unnests an array column into rows
arrayJoinTransform
    : KW_ARRAY_JOIN IDENT (KW_AS IDENT)?
    ;

// sort { [-]col [, [-]col]* }
// '-' prefix = DESC. Without prefix = ASC.
sortTransform
    : KW_SORT '{' sortList '}'
    ;

// take n      → LIMIT n
// take n..m   → LIMIT (m-n) OFFSET n
takeTransform
    : KW_TAKE INTEGER ('..' INTEGER)?
    ;

// skip n → OFFSET n (used after take when n..m shorthand is not enough)
skipTransform
    : KW_SKIP INTEGER
    ;

// window { name = window_func(col) OVER (PARTITION BY ... ORDER BY ...) }
// ClickHouse window functions — expressions are opaque
windowTransform
    : KW_WINDOW '{' assignmentList '}'
    ;

// ─── Sub-rules ─────────────────────────────────────────────────────────────

assignmentList
    : assignment (COMMA assignment)*
    ;
// name = expr   where expr is opaque ClickHouse SQL captured as raw text
assignment
    : IDENT '=' opaqueExpr
    ;

selectionList
    : selectionItem (COMMA selectionItem)*
    ;
// col_name  OR  alias = expr
selectionItem
    : IDENT '=' opaqueExpr
    | opaqueExpr
    ;

keyList
    : keyItem (COMMA keyItem)*
    ;
// plain column ref  OR  alias = expr (for computed grouping keys)
keyItem
    : IDENT '=' opaqueExpr
    | IDENT
    ;

sortList
    : sortItem (COMMA sortItem)*
    ;
sortItem
    : '-' IDENT                     // DESC
    | '+' IDENT                     // ASC (explicit)
    | IDENT                         // ASC (default)
    ;

// opaqueExpr: raw text up to the next structural delimiter ( , } ) or newline )
// The lexer captures this as a single token, respecting nested parentheses.
// ClickHouse expressions — functions, CASE, arithmetic, subexpressions — are not
// parsed further by PQL. They are passed verbatim into generated SQL.
opaqueExpr : OPAQUE_EXPR ;

// ─── Lexer Tokens ──────────────────────────────────────────────────────────

KW_FROM       : F R O M ;
KW_FILTER     : F I L T E R ;
KW_DERIVE     : D E R I V E ;
KW_SELECT     : S E L E C T ;
KW_GROUP      : G R O U P ;
KW_AGGREGATE  : A G G R E G A T E ;
KW_JOIN       : J O I N ;
KW_SIDE       : S I D E ;
KW_INNER      : I N N E R ;
KW_LEFT       : L E F T ;
KW_RIGHT      : R I G H T ;
KW_FULL       : F U L L ;
KW_ARRAY_JOIN : A R R A Y '_' J O I N ;
KW_SORT       : S O R T ;
KW_TAKE       : T A K E ;
KW_SKIP       : S K I P ;
KW_FINAL      : F I N A L ;
KW_WINDOW     : W I N D O W ;
KW_AS         : A S ;

IDENT         : [a-zA-Z_][a-zA-Z0-9_]* ;
INTEGER       : [0-9]+ ;
INDENT        : '  ' | '\t' ;       // two spaces or tab = continuation
COMMA         : ',' ;
NEWLINE       : [\r\n]+ ;
WS            : [ \t]+ -> skip ;

// OPAQUE_EXPR: everything between structural delimiters, balancing ()
// Implemented via lexer mode or custom action in the generated parser.
// Captures: function calls with nested parens, arithmetic, CASE expressions.
OPAQUE_EXPR   : ( ~[,{}\r\n()] | '(' (~[)]* ')') )+ ;

REST_OF_LINE  : ~[\r\n]+ ;

fragment A:[Aa]; fragment R:[Rr]; fragment G:[Gg]; fragment E:[Ee];
fragment F:[Ff]; fragment I:[Ii]; fragment T:[Tt]; fragment N:[Nn];
fragment D:[Dd]; fragment O:[Oo]; fragment V:[Vv]; fragment L:[Ll];
fragment C:[Cc]; fragment S:[Ss]; fragment J:[Jj]; fragment H:[Hh];
fragment K:[Kk]; fragment U:[Uu]; fragment W:[Ww]; fragment M:[Mm];
fragment P:[Pp]; fragment Y:[Yy]; fragment X:[Xx]; fragment B:[Bb];
```

### Schema Propagation Through Transforms

The PQL compiler tracks the active schema after each transform:

```
from orders:
  schema = full DataSource schema
  (static cols: observed_timestamp, user_id, amount, country)
  (attribute registry: status=Int64/95%, env=String/99%, response_time_ms=Float64/99%)

filter status = 200 AND env = prod:
  schema = unchanged (filter narrows rows, never columns)

derive { day = ..., tier = ... }:
  schema = prior + {day: Date, tier: String}
  (toStartOfDay → Date, multiIf with string branches → String)

group { day, country, tier } ( aggregate { revenue = sum(amount), ... } ):
  schema RESETS to aggregate output only:
  {day: Date, country: String, tier: String,
   revenue: Float64, order_count: Int64, unique_users: Int64, p95_latency: Float64}
  [observed_timestamp, user_id, amount, all attributes → out of scope]

join side:left dim_country (country = dim_country.code):
  schema = aggregate schema + dim_country columns

filter revenue > 1000:
  schema = unchanged (post-join filter, revenue is in scope)
  (FilterLang resolves 'revenue' against current schema → direct column, Float64)
```

**Schema reset after `group`** is enforced at compile time. Referencing `observed_timestamp`
in a `filter` after a `group` is an error — the compiler reports it before any SQL is generated.

### SQL Compilation Strategy: Collapse vs CTE

The compiler merges transforms into the smallest number of SQL clauses,
falling back to CTEs when merging would be incorrect.

**Collapse rules** (merge into one SELECT without CTE):
```
from + filter                    → SELECT * FROM t WHERE ...
from + filter + sort + take      → SELECT * FROM t WHERE ... ORDER BY ... LIMIT n
from + filter + select           → SELECT cols FROM t WHERE ...
from + filter + derive + group   → SELECT derived, aggs FROM t WHERE ... GROUP BY ...
  (only when derive exprs are referenced in GROUP BY or aggregate, not post-group)
```

**CTE required when**:
```
filter after group               → post-aggregation WHERE (can't merge into base WHERE)
derive then filter on derived col → derived col isn't available in base WHERE
join after group                 → must join on aggregated result, not base table
any transform after join         → join result needs its own scope
```

**Example: simple pipeline — no CTE needed**

```
from orders
filter country = US
sort { -amount }
take 10
```
```sql
SELECT * FROM orders WHERE country = 'US' ORDER BY amount DESC LIMIT 10
```

**Example: derive then group — single CTE**

```
from orders
filter status = 200
derive { day = toStartOfDay(observed_timestamp) }
group { day, country } (
  aggregate { revenue = sum(amount), orders = count() }
)
sort { -day }
```
```sql
WITH __derive AS (
  SELECT *, toStartOfDay(observed_timestamp) AS day
  FROM orders
  WHERE attributes.status::Int64 = 200
)
SELECT day, country, sum(amount) AS revenue, count() AS orders
FROM __derive
GROUP BY day, country
ORDER BY day DESC
```

**Example: filter after group — two CTEs**

```
from orders
group { country } (
  aggregate { revenue = sum(amount), orders = count() }
)
filter revenue > 10000
sort { -revenue }
take 5
```
```sql
WITH __agg AS (
  SELECT country, sum(amount) AS revenue, count() AS orders
  FROM orders
  GROUP BY country
)
SELECT * FROM __agg
WHERE revenue > 10000
ORDER BY revenue DESC
LIMIT 5
```

### Type Inference for `derive` and `aggregate`

Expressions in `derive` and `aggregate` are opaque — but the compiler pattern-matches
known ClickHouse functions to propagate types into the output schema:

| Expression pattern | Inferred output type |
|-------------------|---------------------|
| `count()`, `count(col)` | Int64 |
| `sum(col)` | same as col |
| `avg(col)` | Float64 |
| `min(col)`, `max(col)` | same as col |
| `uniq*(col)`, `uniqExact(col)` | Int64 |
| `quantile*(n)(col)`, `median(col)` | Float64 |
| `any(col)` | same as col |
| `groupArray(col)` | Array(type of col) |
| `topK(n)(col)` | Array(type of col) |
| `toStartOfDay(col)` | Date |
| `toStartOfHour(col)` | DateTime |
| `toYYYYMM(col)` | Int32 |
| `upper(col)`, `lower(col)`, `toString(col)` | String |
| `toInt64(col)`, `toInt32(col)` | Int64 |
| `toFloat64(col)` | Float64 |
| `multiIf(…, 'str', …)` | String |
| `multiIf(…, n, …)` | Int64 |
| bare column reference | lookup in current schema |
| arithmetic `+`, `-`, `*`, `/` | type promotion |
| everything else | Dynamic |

### JOIN Type Safety

The compiler resolves types on both sides of a join condition and flags mismatches:

```
join side:left dim_country (country = dim_country.code)

Compiler:
  left.country       → String  (from static column)
  dim_country.code   → String  (from dim_country DataSource schema)
  → Match: String = String → safe

join side:left sessions (user_id = sessions.uid)

Compiler:
  left.user_id       → String  (static column)
  sessions.uid       → Int64   (from sessions schema)
  → MISMATCH
  → Error: "Join key type mismatch: user_id (String) vs sessions.uid (Int64)"
  → Suggestion: (user_id = sessions.uid::String)
  → Auto-fix: --auto-cast generates CAST(sessions.uid AS String)
```

### ClickHouse-Specific Extensions

**`from table FINAL`** — for ReplacingMergeTree (reads latest version of each row):
```
from orders final
filter status = 200
```
→ `SELECT * FROM orders FINAL WHERE ...`

**`array_join col`** — ClickHouse ARRAY JOIN (unnests array into rows):
```
from orders
array_join tags
filter tags = priority
group { tags } ( aggregate { count = count() } )
```
→ `SELECT tags, count() AS count FROM orders ARRAY JOIN tags WHERE tags = 'priority' GROUP BY tags`

**`window { ... }`** — ClickHouse window functions (opaque, passed through):
```
from orders
window {
  running_total = sum(amount) OVER (PARTITION BY country ORDER BY observed_timestamp)
}
select { country, amount, running_total }
```

## ClickHouse Version Compatibility

New JSON type dot-notation (`attributes.env::String`) is production-ready in ClickHouse 25.3+.
For older versions: `JSONExtractString(attributes, 'env')`. Both work with `JSON(max_dynamic_paths=0)`.

| CH version | Attribute access in generated SQL |
|------------|---------------------------------|
| ≥ 25.3 | `attributes.field::Type` |
| 24.x | `JSONExtractString(attributes, 'field')` etc. |
| < 24.0 | same as 24.x |

The compiler detects version at startup (`SELECT version()`) and sets a flag once.

## Open Questions

1. **Filter multi-line continuation**: indented lines after `filter` are continuation of
   the same FilterLang expression, joined without any implicit operator. Users write explicit
   `AND` / `OR` across lines. Alternative: implicit AND per line (simpler). Current design:
   explicit — full FilterLang expression spanning lines.

2. **`group { key = expr }` vs `derive` then `group { key }`**: PRQL allows computed keys
   directly in the `group {}` list (`group { day = date.trunc 'day' ts }`). We allow the
   same syntax (`group { day = toStartOfDay(observed_timestamp) }`). This means `derive`
   is optional for keys — but then schema propagation must handle key expressions too.
   Simpler: always `derive` first, then `group` with bare column names. But that's more verbose.

3. **Multiple `filter` transforms**: the design allows `filter` at any position in the
   pipeline (before and after `group`, before and after `join`). The compiler decides
   WHERE vs post-aggregation WHERE vs HAVING based on which schema the filtered columns
   belong to. This is the right behavior but must be tested carefully.

4. **`take n..m` range syntax**: PRQL's `take 10..20` means rows 10–20 (0-indexed OFFSET 10
   LIMIT 10). Natural but non-obvious. Alternative: keep separate `take` and `skip` always.
   Current design: both `take n..m` and `take n` + `skip m` are supported.

5. **ClickHouse version enforcement**: require ≥ 25.3 for all new DataSources (cleaner SQL
   generation) or maintain fallback indefinitely? Proposal: compile-time warning when
   connecting to < 25.3, fallback always available, deprecate fallback in a future major version.
