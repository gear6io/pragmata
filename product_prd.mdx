TinyBird's core insight: **ClickHouse is powerful but unapproachable**. Their solution is elegant:

```

```

### What they built well

| Capability | What it does |
|------------|-------------|
| **Pipes** | Chained SQL nodes, last node exposed as REST endpoint |
| **Events API** | HTTP endpoint to stream JSON events directly into ClickHouse |
| **Tokens** | API key management with per-pipe scopes |

| **Copy Pipes** | Scheduled SQL-to-table writes with cron |
| **Environments** | Dev/staging/prod branching for safe iteration |

| **BI Compatibility** | Native ClickHouse interface for Grafana, Tableau, Power BI |
| **ClickHouse Fork** | Custom optimizations — 30-40% fewer S3 writes, 30% faster PREWHERE |

Their `.pipe` file format is clean. Their developer experience is thoughtful. They deserve credit.

### Their architectural moat

TinyBird maintains a **private ClickHouse fork** with proprietary optimizations:
- **Packed Part Format**: Combines small MergeTree files → 30-40% reduction in S3 write ops
- **Inplace filtering** on PREWHERE stage → ~30% faster query execution
- Custom UNION support for materialized views

This fork gives them a real performance edge. We need to understand and counter this honestly.

## 4. ClickHouse's Real Developer Pain — What We're Actually Solving

This is more important than TinyBird feature parity. ClickHouse has six well-documented,
serious operational pain points that a platform layer can solve:

### 1. "You are the optimizer"

ClickHouse has no query optimizer. If you choose the wrong sort key, your queries are 10-100x
slower. There's no guardrail. A platform with schema linting, sort key recommendations, and
query analysis baked into the CLI catches this before production.

### 2. Schema migrations are career-limiting

You cannot change a sort key on an existing table. The only option is rebuild the table from
scratch — meaning a full data reload. For production tables with billions of rows, this is a
24-72 hour operation with zero downtime guarantee. A platform layer with migration planning,
shadow tables, and safe swap tooling makes this solvable.

### 3. Materialized Views are unreliable by default

> "MVs operate asynchronously relative to the statement that creates or inserts data into them."
> — CloudQuery Engineering Blog

This means: you insert data, you query the MV, the data might not be there yet. No visibility
into failures. Unpredictable freshness for API responses. Our platform needs guaranteed-freshness
semantics or at least explicit freshness metadata on every API response.

### 4. JOINs are footguns

Large fact table JOINs with dimension tables frequently produce memory overcommit errors that
terminate queries silently. Developers don't know why their query died. A platform with query
analysis and JOIN pattern recommendations changes the experience entirely.

### 5. ClickHouse functions are not discoverable

The ClickHouse function library is massive and non-standard. `toStartOfDay`, `arrayJoin`,
`runningAccumulate`, `groupBitmap` — these exist nowhere else. A platform with intelligent SQL
autocomplete, semantic search over functions, and AI-assisted query generation is transformative.

### 6. Migration between deployments is painful

Moving from ClickHouse Cloud to self-hosted (or vice versa) requires config rework, query
rewriting, and behavioral differences. A platform that abstracts this with a consistent interface
locks in users at the platform layer, not the cluster layer.

## 6. What Makes Us Genuinely Better Than TinyBird

These are not feature flags. These are philosophical differences.

### 1. Bring Your Own ClickHouse

You point our platform at any ClickHouse instance — self-hosted, ClickHouse Cloud, Altinity,
any managed provider. We never touch your data. We're a developer platform, not a database host.
TinyBird cannot offer this by design. We can offer it by design.

### 2. Open Source First, Cloud Second

Our entire platform is open-source (Apache 2.0). The cloud-hosted version is identical to what
you run locally. This is the Supabase playbook and it is the correct playbook. OSS drives:
- Community-led bug fixes and feature requests
- AI code generation training data (Cursor/Claude will "know" our platform)
- Trust and auditability that a closed SaaS can never provide
- Developer advocacy that doesn't need a budget

### 3. Standard SQL + Standard Templating

We don't invent a proprietary template syntax. We use **Jinja2** (the standard) and follow
SQLMesh's approach for macro definitions. Any developer who knows Jinja2 is immediately
productive. TinyBird's `{{ String(x, 'y') }}` is a learning tax we don't charge.

### 4. Column-Level Lineage

SQLMesh gives us column-level lineage out of the box. You can trace any column in any API
response back through every Pipe node to the source table. TinyBird has no lineage system.
This is a significant enterprise differentiator.

### 5. Data Contracts

Define explicit schemas between Pipes and Data Sources. Teams can evolve independently without
breaking downstream consumers. This is an enterprise feature TinyBird does not have.

### 6. Migration Safety

Our CLI includes:
- Sort key validation before table creation
- Safe schema migration via shadow table pattern
- Backfill planning for incremental model changes
- Dry-run mode for all destructive operations

### 7. Freshness Guarantees

Every API response includes a `freshness` metadata field. Materialized views include an explicit
SLA. If a MV is behind its SLA, the endpoint automatically falls back to live query (configurable).
This solves ClickHouse's async MV problem at the platform layer.

### 8. Multi-Environment Deployments (Better Than TinyBird's)

SQLMesh's virtual environments become our branching system. A developer can create a `feature/
new-sales-pipe` environment that references the production ClickHouse cluster but isolates schema
changes using SQLMesh's shadow-schema approach. No data duplication. Full safety.

### 9. AI-Native from Day One

Not a chatbot gimmick. Three specific AI capabilities:
- **Natural language to Pipe**: Describe what you want in English, get a `.pipe` file
- **Query explanation**: "Why is this Pipe slow?" → AI analyzes query plan + schema
- **Function discovery**: "I need to aggregate by rolling 7-day window" → suggests the right
  ClickHouse function with example

## 8. Phase 1 MVP — TinyBird Parity

Goal: Any TinyBird user can migrate to us with a weekend of work.

### Core Primitives

**Pipes** — the central product concept

```
# sales.pipe
DESCRIPTION Daily revenue by country with pagination
TAGS revenue, sales

NODE aggregate
SQL >
  %
  SELECT
    toStartOfDay(created_at)   AS day,
    country,
    sum(amount)                AS revenue,
    count()                    AS orders
  FROM orders
  WHERE
    {% if defined(country) %}
    country = {{ country | default('US') }} AND
    {% endif %}
    created_at >= {{ start | default('2024-01-01 00:00:00') }}
  GROUP BY day, country

NODE paginate
SQL >
  %
  SELECT * FROM aggregate
  ORDER BY day DESC
  LIMIT  {{ limit | int | default(100) }}
  OFFSET {{ page | int | default(0) * limit | int | default(100) }}

TYPE ENDPOINT
```

**Data Sources** — schema + ingestion config

```yaml
# orders.datasource
SCHEMA >
  `id`         UInt64,
  `created_at` DateTime,
  `country`    LowCardinality(String),
  `amount`     Float64

ENGINE MergeTree
ENGINE_SORTING_KEY created_at, country
```

**Three Pipe types** that cover ~95% of TinyBird use cases:

| Type | What it does | API |
|------|-------------|-----|
| `ENDPOINT` | Live parameterized query | `GET /v0/pipes/{name}?param=val` |
| `MATERIALIZED` | Pre-aggregated ClickHouse MV | Populated at ingest time |
| `COPY` | Scheduled writes to target table | `COPY_SCHEDULE 0 * * * *` |

**Events API** — `POST /v0/events?name=orders` — NDJSON, CSV, Parquet. Returns:
```json
{"successful_rows": 1000, "quarantined_rows": 0}
```

**Token system**:
- Generate scoped API keys (`PIPES:READ`, `DATASOURCES:WRITE`)
- Auth via header (`Authorization: Bearer xxx`) or URL param (`?token=xxx`)
- SQLite storage locally; Postgres in cloud

**REST Response Envelope** (TinyBird-compatible for migration path):
```json
{
  "data": [{"day": "2024-01-15", "country": "US", "revenue": 45230.50}],
  "meta": {"columns": [{"name": "day", "type": "Date"}, ...]},
  "stats": {"elapsed": 0.032, "rows_read": 50000},
  "freshness": {"last_updated": "2024-01-15T10:00:00Z", "lag_seconds": 3}
}
```

### MVP Technical Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                    Go Service (`pipe`)                        │
│                                                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌────────────┐ │
│  │  Parser  │  │ Template │  │ Executor │  │   Server   │ │
│  │ .pipe    │  │ Jinja2   │  │ CTE      │  │ gin HTTP   │ │
│  │ .datasrc │  │ standard │  │ chain    │  │ /v0/pipes  │ │
│  └──────────┘  └──────────┘  └──────────┘  └────────────┘ │
│                                                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────────────┐ │
│  │  Auth    │  │ Ingest   │  │  SQLMesh subprocess       │ │
│  │  Tokens  │  │ Events   │  │  (Materialized + Copy)    │ │
│  │  SQLite  │  │  API     │  │  sqlmesh apply / run      │ │
│  └──────────┘  └──────────┘  └──────────────────────────┘ │
└──────────────────────────┬──────────────────────────────────┘
                           │ clickhouse-go/v2
                    ┌──────▼──────────┐
                    │   ClickHouse    │
                    │ (any instance)  │
                    └─────────────────┘
```

**SQLMesh's role in Phase 1**: Materialized view orchestration only. We call `sqlmesh apply`
and `sqlmesh run` via subprocess. SQLMesh handles incremental model state, environment tracking,
and ClickHouse MV creation. We don't re-implement what SQLMesh already does well.

**What SQLMesh contributes**:
- ✅ Incremental model tracking (what intervals have been processed)
- ✅ Virtual environment management (dev/staging/prod schema isolation)
- ✅ Column-level lineage (tracked through SQL model graph)
- ✅ Multi-database support (future: DuckDB, Postgres fallback)
- ✅ Data contract framework (Phase 2)

**What SQLMesh does NOT do** (we build these):
- ❌ HTTP API serving layer
- ❌ Token auth and API key management
- ❌ Events/ingestion API
- ❌ `.pipe` file format and parser
- ❌ Request-time SQL templating
- ❌ Rate limiting, response formatting

### CLI

```bash
[product] init                      # Scaffold project with example pipes + config
[product] dev                       # Start local ClickHouse + API server (Docker)
```

The `dev` command is the killer local experience. One command starts everything.

### TinyBird Migration Path

`[product] migrate --from tinybird --token xxx`:
1. Pulls all `.pipe` and `.datasource` files from TinyBird via their CLI export
2. Converts TinyBird's template syntax to standard Jinja2
3. Generates our `.pipe` format equivalents
4. Reports what can be auto-migrated vs what needs manual review

**Syntax conversion:**

| TinyBird | Ours |
|---------|------|
| `{{ String(country, 'US') }}` | `{{ country \| default('US') }}` |
| `{{ Int32(limit, 100) }}` | `{{ limit \| int \| default(100) }}` |
| `TOKEN dashboard READ` | Managed via `[product] token` commands |
| `TYPE MATERIALIZED\nDATASOURCE name` | `TYPE MATERIALIZED\nDATASOURCE name` (same) |

## 12. SQLMesh — Role, Strengths, and Limits

### What SQLMesh provides

| Capability | Our Phase |
|------------|-----------|
| Virtual environments (dev/staging/prod isolation) | 1 |
| Incremental model state tracking | 1 |
| Automatic backfill planning | 1 |
| Column-level lineage | 2 |
| Data contracts / schema validation | 2 |
| dbt project compatibility | 3 |
| Multi-dialect SQL transpilation | 3 |

### What SQLMesh is not

SQLMesh is a transformation framework, not a serving platform. It has no HTTP layer, no token
auth, no events ingestion, no real-time subscriptions, no request-time SQL templating.

**Our division**: SQLMesh manages data (transformation, state, scheduling). We manage queries
(serving, auth, real-time, developer experience).

### Integration approach

- **Phase 1**: SQLMesh via subprocess for materialized/copy pipe execution
- **Phase 2**: Tighter Python-Go bridge (gRPC or local socket) for real-time status, lineage
  queries, schema inspection
- **Phase 3**: SQLMesh deeply embedded — lineage UI is built on SQLMesh's lineage graph,
  dbt project compatibility via SQLMesh's transpilation layer

## 18. The Founding Insight

TinyBird built a beautiful product on a closed foundation. They will always be limited by the
fact that you cannot self-host them, cannot bring your own cluster, cannot inspect how they work,
cannot contribute to them, and cannot escape their pricing tiers.

We build the same beautiful product on an open foundation. The product can be as good or better.
The community cannot be replicated.

ClickHouse is where PostgreSQL was in 2018 — powerful, fast, increasingly popular, but
unapproachable to the average developer. Supabase changed that for Postgres in 4 years.

The name of the category we're creating: **Analytical API Platform.**

The winner of that category will be worth building.
